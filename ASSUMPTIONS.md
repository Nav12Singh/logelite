  - `min_price`/`max_price` are read natively by `price_filter_post_clauses()` — no query tweak needed.
  - `filter_{attribute}` is read natively by `get_layered_nav_chosen_attributes()`, but **as comma-joined term SLUGS, not term IDs** (each value is run through `sanitize_title()` and matched with `'field' => 'slug'`). The task said "term IDs" — I used slugs instead since that's what actually works with zero extra query code; using literal IDs would have required `lgl_filter_products()` to translate them anyway, for no benefit.
  - Native HTML checkboxes can't produce WC's expected *single* comma-joined value from several same-named inputs without JS — so `filter_{attribute}[]` (array form, works correctly with zero JS) is submitted, and `lgl_normalize_attribute_filter_query_vars()` (`inc/woocommerce.php`, on `wp_loaded`) rewrites it into the comma-joined string before WooCommerce's `pre_get_posts` handling reads it. This runs on `wp_loaded` rather than `woocommerce_product_query` specifically because `WC_Query` already reads the chosen attributes while building its tax_query earlier in the same `pre_get_posts` pass, before `woocommerce_product_query` fires — that hook would be too late.
  - `on_sale`/`in_stock` have **no** native WC query handling at all — confirmed by grep, no matches anywhere in core. `lgl_filter_products()` (on `woocommerce_product_query`, exactly as the task anticipated) implements both.
- **Category filtering is a link list, not a multi-select filter** — the task's own wording for this block ("hierarchical product_cat list with counts, current term marked `aria-current`") describes navigation, not a GET-param filter (unlike price/attributes, which the task describes in explicit GET-param terms). WooCommerce also has no native multi-category URL filter to read anyway — category browsing works by navigating to that category's own archive.
- **Active filter chips are rendered in the toolbar**, not the sidebar, per archive-product.php's more specific "Toolbar row: result count | active filter chips | orderby | view toggle" spec (the filters.php bullet also mentions them, but doesn't contradict this placement). Built as its own `template-parts/shop/active-filters.php`, called only from the toolbar.
- **Shop hero banner image reuses the same `thumbnail_id` term meta** already used for the homepage category-grid thumbnails — WooCommerce's category edit screen only has one image field, there's no separate "banner" meta to read. Rendered at the `lgl-hero` (1920×900) size instead of `lgl-card`.
- `content-product.php`: replaced the full default hook stack with one `lgl_product_card()` call, but kept `woocommerce_before_shop_loop_item` and `woocommerce_after_shop_loop_item_title` firing (with nothing of ours hooked to them) specifically so third-party plugins hooking into those two survive the override — documented in the file itself as the task asked.
- `loop/orderby.php`, `loop/result-count.php`, `loop/no-products-found.php` keep their upstream logic byte-for-byte functionally identical — only `lgl-*` BEM classes were added for restyling via `assets/css/pages/shop.css`, plus the required "Overridden by logelite" comment. `loop/pagination.php` has real logic changes: `mid_size` 3→1, SVG prev/next arrows replacing `&larr;`/`&rarr;`, and its `aria-label` string moved to this theme's `logelite` text domain since the string is now maintained here.
- `loop/loop-start.php`/`loop/loop-end.php` were **not** copied (not in the task's list) — `shop.css`'s column-count grid rules target the `columns-{n}` class WooCommerce's own (uncopied) `loop-start.php` already outputs from the same `loop_shop_columns` value `lgl_loop_columns()` filters, so no inline style or CSS variable hack was needed for the Customizer-driven column count.
- Price range bounds are cached via a daily transient reading `{$wpdb->prefix}wc_product_meta_lookup` (WooCommerce's own fast lookup table for min/max price) directly, rather than scanning postmeta.

## Single product templates, inc/woocommerce.php summary reorder, assets/js/product.js, assets/css/pages/product.css

- **"breadcrumb/category" is rendered outside `woocommerce_single_product_summary` entirely**, in `content-single-product.php`, before the two-column layout — not literally hooked to that action like the rest of the priority map. Anything hooked to `woocommerce_single_product_summary` is confined to the (right-hand, ~50%-width) summary column; the design reference shows the breadcrumb full-width above the whole product block, which is only achievable by rendering it outside that hook. Documented in both the template and the priority-map comment.
- **Layout is a literal two-column split (gallery / summary)**, per the task's explicit instruction — design-reference actually uses three columns (image / product details / a separate sticky buy-box with its own border). Reconciled by folding the reference's "buy-box" content (price, stock, quantity, add-to-cart) into the single right-hand summary column alongside title/rating/description/meta, since the task's hook-priority spec (one combined `woocommerce_single_product_summary` stack) doesn't describe a separate buy-box mechanism.
- **Gallery thumbnail orientation verified against the actually-installed WooCommerce**, not guessed: `assets/js/frontend/single-product.js` initializes flexslider directly on `.woocommerce-product-gallery__wrapper`, and `includes/class-wc-frontend-scripts.php` passes `controlNav: 'thumbnails'`, which flexslider's own code (`assets/js/flexslider/jquery.flexslider.js`) turns into a real `<ol class="flex-control-nav flex-control-thumbs">` — those are the exact classes `product.css` targets, not assumed ones. Note: design-reference's actual product page shows thumbnails in a horizontal row *below* the main image; the task's literal text ("vertical strip on desktop, horizontal on mobile") was followed instead, since it's an explicit written instruction.
- **`global/quantity-input.php`'s -/+ buttons affect every quantity input site-wide** (cart line items, mini-cart), not just the single product page — it's WooCommerce's one shared template for all of them, and the task's own parenthetical ("actually global/quantity-input.php") shows this was understood going in.
- **Tabs→accordion requires a real DOM move, not CSS alone**: WooCommerce's markup keeps all tab headers in one `<ul>` and every panel as a flat sibling afterward, which can't be visually interleaved (header immediately above its own content) with CSS given that shape. `assets/js/product.js` moves each panel `<div>` inside its own `<li>` below 767px (valid HTML — content inside `<li>`, not a `<div>` sibling of `<li>` inside `<ul>`) and reverses this above that breakpoint. To stop the accordion's click handling and WooCommerce's own native tab script from fighting over the same clicks, the accordion handler is attached in the *capture* phase with `stopImmediatePropagation()`, and only takes over below the breakpoint — above it, WooCommerce's own script runs completely untouched.
- `WC_Structured_Data::generate_product_data()` isn't in the task's named priority list, but had to be explicitly relocated (default priority 60 would collide with the new `lgl_product_feature_icons_placeholder` slot) — moved to priority 100 (last), harmless since it only outputs an invisible JSON-LD `<script>`. Removing/re-adding it requires the exact same object instance WooCommerce itself uses (`WC()->structured_data`), not a class-name string, since it was originally hooked as `array( $this, 'generate_product_data' )` from inside the class's own constructor.
- T3 hook targets left empty, with TODO comments, exactly per the scope guard: `lgl_sticky_add_to_cart` (action, fired from `content-single-product.php` above the layout), `lgl_product_feature_icons` and `lgl_delivery_estimator` (actions, fired from their respective placeholder functions on the summary hook). FAQ and the related-products carousel need no new hook — FAQ will add a tab via the existing `woocommerce_product_tabs` filter (noted inline in `tabs.php`), and the carousel will restyle `woocommerce_output_related_products()`'s existing output (noted inline in `content-single-product.php`).
- `woocommerce/global/breadcrumb.php` was copied with zero logic changes — it's a generic renderer of whatever wrap/delimiter strings `woocommerce_breadcrumb()` passes in, so the actual `.lgl-breadcrumbs`-matching restyle was done via the `woocommerce_breadcrumb_defaults` filter (`lgl_breadcrumb_defaults()`) instead of editing the template.

## Cart and checkout templates, assets/js/{quantity,cart}.js, assets/css/pages/checkout.css

- **The task said "data-label"; the actual attribute WooCommerce's own `cart.php` outputs is `data-title`** (verified by reading the real template rather than assuming) — `checkout.css`'s mobile card layout targets `[data-title]::before`, the attribute that's actually there.
- **No hooks were removed for this task at all.** Every requested layout change (cart's two-column split, checkout's billing/payment-left vs. summary/place-order-right split) was achievable with wrapper markup + CSS alone, so `inc/woocommerce.php` gets no new `remove_action()` calls here.
- **Checkout's column split uses a three-level `display: contents` cascade** (`form.checkout` → `#order_review` → `#payment`, all in `assets/css/pages/checkout.css`) so their real children — `#customer_details`, the coupon form, the review-order table, the payment-method list, and the place-order block — become direct items of one CSS Grid (`grid-template-areas`), each positioned by `grid-area`. Zero PHP/hook changes were needed to achieve the split; every action and both nonces (`woocommerce-process-checkout-nonce`, `woocommerce-cart-nonce`) stayed exactly where WooCommerce puts them.
- **One deviation from the literal column split, documented rather than hidden:** the shipping-method radio list ("delivery option") is generated by `wc_cart_totals_shipping_html()` as a `<tr>` inside the review-order table's `<tfoot>`. Extracting a table row into a different CSS Grid area via `display: contents` is unreliable across browsers (table-part `display` values have known inconsistencies), so it was left in place — restyled as radio cards (`woocommerce/cart/cart-shipping.php`), but physically rendering in the right-hand order-summary column instead of the left column the task described.
- **Sticky is applied per-piece, not as one unified card**, for the same structural reason: because `#order_review` is flattened so its children can scatter across grid areas, there's no single wrapper left to make the whole right column stick together. Only `.lgl-place-order` (the actual place-order button block) is sticky, pinned to the *bottom* of the viewport as the shopper scrolls the (often long) billing/shipping/payment form — a deliberate choice, since keeping the completion button reachable matters more than the summary table once the two are structurally separated.
- `checkout/form-coupon.php` has **no nonce field of its own** — checkout coupon application submits via WooCommerce's core AJAX (`wc-ajax=apply_coupon`), whose nonce is localized separately in core JS and was never part of this template. Its `is_coupon_form`-style toggle logic (the `showcoupon` link + `aria-expanded`/`aria-controls` pairing) is unchanged.
- `checkout/review-order.php` adds line-item **thumbnails**, which upstream doesn't include, and wraps the table in a native `<details open>` with a `<summary>` (item count + running total via `WC()->cart->get_total()`) — genuinely collapsible only below 768px via CSS disabling/enabling the `<summary>`'s interactivity; no JS needed either way.
- The quantity stepper's JS was extracted into a new shared `assets/js/quantity.js` (used by both `product.js` and the new `cart.js`), since `woocommerce/global/quantity-input.php` — and its `-`/`+` buttons — is one shared template used by both pages, not two separate ones.
- `assets/js/cart.js` debounces (500ms) the auto-click of the existing "Update cart" button after a quantity `change`, so repeatedly clicking the `+`/`-` stepper doesn't fire several form submissions back to back. The button itself is untouched and still works with JS fully disabled.
- `checkout/thankyou.php`'s T4 delivery-details placeholder uses a new custom action, `do_action( 'lgl_thankyou_delivery_details', $order )` — not named in the task, but consistent with the `lgl_product_feature_icons`/`lgl_delivery_estimator` placeholder pattern from the product-page task, giving T4 a clean, empty, documented attachment point rather than requiring it to restructure this file later.
