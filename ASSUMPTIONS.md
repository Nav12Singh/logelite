## inc/enqueue.php

- **Fonts are self-hosted, not fetched.** `design-reference/Logelite Theme.dc.html` loads Google Fonts via `<link href="https://fonts.googleapis.com/css2?family=Archivo:wght@500;600;700;800&family=Public+Sans:wght@400;500;600;700&display=swap">`. Per the hard "no CDN assets" rule, `_tokens.css` declares local `@font-face` rules for both families instead.

  **Resolved (post-T6):** the WOFF2 files were missing on disk, which is what produced the 404s reported in the browser console for all 8 `archivo-*`/`public-sans-*` paths. Fetched the same Google Fonts CSS2 endpoint the reference design links to (one-time, build-time asset acquisition — not a runtime CDN call), and downloaded the resulting `fonts.gstatic.com` static file for each family's plain-Latin unicode subset, then saved local copies at every path `_tokens.css` already expects:
  - `assets/fonts/archivo/archivo-500.woff2`, `-600.woff2`, `-700.woff2`, `-800.woff2`
  - `assets/fonts/public-sans/public-sans-400.woff2`, `-500.woff2`, `-600.woff2`, `-700.woff2`

  Note: Google served the *same* underlying file for every Archivo weight (500–800) and every Public Sans weight (400–700) within a given unicode subset — both families are shipped as variable fonts, and Google's CSS2 API reuses one variable-font file across several discrete `font-weight` static `@font-face` declarations, relying on browsers' standard "implicit variable-instance matching" (CSS Fonts 4) to render each declared weight correctly from the file's `wght` axis. So the 4 Archivo files (and 4 Public Sans files) on disk are intentionally byte-identical per family — this is not a copy-paste mistake, and verified via `curl` that all 8 paths now return HTTP 200 instead of 404.
- `lgl_asset_version()` falls back to `wp_get_theme()->get( 'Version' )` when a referenced asset doesn't exist yet on disk — several handles registered here (`lgl-app`/theme root `style.css`, `lgl-components`, `assets/css/pages/{home,product,checkout,shop}.css`, `assets/js/navigation.js`) point at files not yet created; they are placeholders for upcoming tasks, not 404s to fix now.
- `lgl-components` is registered as a single aggregate `assets/css/components.css`, not the `components/` subfolder shown in CLAUDE.md §3. There's no build step defined anywhere in the project to compile multiple partials into one file, so a single flat file is the only way to give it one enqueued handle. If `components/` should hold multiple files instead, they'll need a manual `@import` or a build step — flagging for a decision.
- `wp_localize_script` i18n strings for `lgl-navigation` (`menuOpenLabel`, `menuCloseLabel`) are placeholder copy — exact strings weren't specified. Object name chosen: `lglNavigation`.
- Nonce action `lgl_nonce` and `admin_url( 'admin-ajax.php' )` are localized onto `lgl-navigation` per the task, even though no navigation-triggered AJAX call exists yet (the delivery estimator AJAX endpoint described in CLAUDE.md §3 lives in `inc/ajax.php`, not here) — wiring is in place for whichever script ends up needing it.

## inc/ajax.php delivery REST route, inc/helpers.php delivery map/lookup, template-parts/product/delivery-estimator.php, assets/js/delivery.js

- **REST route, not admin-ajax.php** — `POST /wp-json/lgl/v1/delivery`. Chosen per instruction for a versioned namespace, a directly-testable/curl-able URL, real HTTP status codes (400/403/429) instead of an always-200 admin-ajax response body, and built-in per-arg validation/sanitization via the route's `args` schema. Documented as a code comment at the top of `inc/ajax.php`.
- **Pincode format assumed Indian** (6 digits, first digit 1-9, `/^[1-9][0-9]{5}$/`) — the brief's own examples (110001, 560001) are Indian PIN codes and no other locale was specified.
- **The delivery map and zone-prefix tables are dummy data**, as the brief permits: `lgl_get_delivery_map()`'s five exact pincodes were given; the zone-prefix fallback (`lgl_get_delivery_zone_prefixes()` / `lgl_get_delivery_zone_defaults()`) was invented to satisfy "prefix fallback → a zone table (metro / tier-2 / rest)" — the specific prefixes assigned to "metro" and "tier_2" are illustrative major-city picks, not a real logistics zone map. Both are `apply_filters()`-wrapped so a real integration can override them without editing theme code.
- **COD default for the 'rest' zone (no prefix match) is inferred as `false`** — the brief specified the 5-7 day window for that zone but not a COD default; unavailable was chosen as the more realistic assumption for unmapped/remote areas. Logged here per §11.6.
- **Business-day calculation skips Saturday/Sunday via a simple day-by-day loop** (`lgl_add_business_days()`) with no public/bank holiday calendar — an explicit simplification per the brief ("simple loop, no holiday calendar").
- **Nonce mechanism**: the route's `permission_callback` is `__return_true` (required — WordPress would trigger `_doing_it_wrong()` if left null/unset, and the endpoint is intentionally public so any shopper can check delivery pre-purchase). Actual request legitimacy is enforced *inside* `lgl_rest_check_delivery()` itself: it reads the `X-WP-Nonce` request header and calls `wp_verify_nonce( $nonce, 'wp_rest' )`, rejecting with a 403 `WP_Error` if missing/invalid. The front end sends this via `wp_localize_script( 'lgl-delivery', 'lglDelivery', [ 'nonce' => wp_create_nonce( 'wp_rest' ), ... ] )` (`inc/enqueue.php`) and an `X-WP-Nonce` fetch header (`assets/js/delivery.js`).
- **Rate limiting** (`lgl_delivery_rate_limited()`) is a `get_transient()`/`set_transient()` fixed-window counter, 20 requests per 60 seconds, keyed on `md5( ip + wp_salt() )` so the transient name never exposes a raw IP. It is not atomic/lock-protected — under true concurrent requests from the same IP within the same second, the read-then-write could under-count by a request or two. Acceptable for a public read-only lookup endpoint; noted as a simplification, not a general-purpose rate limiter.
- **IP source is `REMOTE_ADDR` only** (`lgl_get_client_ip()`), never `X-Forwarded-For` or any other client-supplied header, since those are spoofable by the very client the rate limit is meant to constrain. Sites behind a proxy that doesn't rewrite `REMOTE_ADDR` correctly would rate-limit all visitors together — an infrastructure/server-config concern, out of scope for theme code.
- **Filter names introduced**: `lgl_delivery_map`, `lgl_delivery_zone_prefixes`, `lgl_delivery_zone_defaults`, `lgl_delivery_blocked` (unserviceable-pincode list, empty by default), `lgl_delivery_result` (final response array, filterable by pincode/product ID — the intended hook for a real per-product or real-logistics-API override).

Documented as a comment in both the template and the JS file.

The markup carries BEM-style classes (`lgl-delivery-estimator`, `__label`, `__row`, `__input`, `__button`, `__result`, `__message`, `--success`, `--error`) ready for a follow-up styling pass, but currently renders unstyled (browser-default input/button).

## T3 audit — two real bugs found and fixed, one edge case flagged (not fixed)

- **Bug fixed: `lgl_render_sticky_cart()`'s `! $product->is_purchasable()` bail silently killed the sticky bar for every grouped and every external product, with no exceptions.** WooCommerce hardcodes `is_purchasable()` to always return `false` for both `WC_Product_Grouped` and `WC_Product_External` (verified by reading `class-wc-product-grouped.php` / `class-wc-product-external.php` directly — neither is a real "is there something to sell" check for those types, since only a grouped product's children are purchasable, and an external product's "purchase" is an off-site redirect). 'a' : 'b'`) for boolean-style HTML attributes (`open`, `hidden`, `true`/`false`) were not wrapped in an escaping function** — in `inc/meta-boxes.php` (FAQ row `<details open>`, the repeater empty-state `hidden`), `template-parts/product/faq.php` (front-end `<details open>`), and `template-parts/carousel.php` (`data-show-dots`/`data-autoplay`, plus a `aria-labelledby` attribute built via string concatenation inside a ternary). - **Caught and fixed a real bug before it shipped: an early draft of the reduced-motion block set `.lgl-faq__body-wrapper { transition: none; }`, copying the pattern already used for the chevron just above it.** That's exactly the mistake motion.css's (T5.0) own `0.01ms`-not-`0s` reasoning exists to prevent: a fully-disabled transition (`none`) never fires `transitionend` at all, and `faq-toggle.js`'s close handler depends on that event firing to know when to remove `[open]`. With that rule in place, clicking to close an open FAQ under forced `prefers-reduced-motion` would have left the panel stuck open forever — the collapse would start, no `transitionend` would ever come, and `[open]` would never be removed. Fixed by removing that rule entirely and leaning on motion.css's own global override instead (which forces `transition-duration` to `0.01ms`, not `none` — a real, still-event-firing, just very fast transition). The chevron's own `transition: none` was left alone, since nothing in JS listens for its transition to end.
- **Known, unavoidable limitation, not fixed**: T3.4's exclusive-accordion behavior (`<details name="...">`, native in newer browsers; a JS fallback in `faq.js` for older ones) can close a *different*, previously-open panel the instant a new one opens — either natively (browser-driven) or via `faq.js`'s own `sibling.open = false` fallback (JS-driven, but not through a click on that sibling's own `<summary>`). Neither path goes through `faq-toggle.js`'s click interception, so that sibling always snaps shut instantly rather than collapsing smoothly, regardless of which of the two mechanisms caused it. The native `toggle` event isn't cancelable and fires only after the state change already happened, so there is no hook available to animate this specific case — documented in both `faq.css` and `faq-toggle.js` rather than worked around, since there isn't a real workaround within `<details>`'s event model.
- **Not addressed, flagged instead: the chevron's 180° rotation stays tied purely to `[open]`, unchanged from T3.4** — meaning during the (now delayed) closing animation, the chevron stays fully rotated for the entire collapse and only snaps back to resting the instant `[open]` is actually removed at the very end, rather than rotating back in sync with the content collapsing. Decoupling it would need its own JS-driven class (mirroring the wrapper's inline-style approach) — real, extra machinery beyond what this ticket asked for ("the minimum JS needed... for this specific reason only"). Left as a known, minor visual mismatch rather than solved unprompted.

## Post-T6 — root cause of the blank front-end pages found and fixed: `template-parts/components/breadcrumbs.php`

**Corrects T6's own entry above.** T6 spent significant effort investigating a live blank-page bug and concluded it "may be" related to an incomplete WooCommerce database install, without finding the actual cause. The real cause was much simpler and entirely code-level: `lgl_breadcrumbs()` called `wc_get_breadcrumb()` — a function that **does not exist anywhere in WooCommerce core**, verified by grepping the entire plugin. Every page that renders breadcrumbs (which, via `woocommerce/archive-product.php` and others, is most of the site) hit a fatal "call to undefined function" error. WordPress's own fatal-error handler was producing the 0-byte responses T6 observed; `WP_DEBUG_DISPLAY`/`display_errors` being toggled on/off in that ticket didn't surface it because the error only became visible once WordPress's own "critical error" recovery-mode page rendered it to the browser (which happened after this entry, once the user hit the error directly in a real browser rather than via `curl`).

- **Fixed** by replacing the bogus call with the exact pattern WooCommerce's own `woocommerce_breadcrumb()` template function uses internally (verified by reading it directly): instantiate `WC_Breadcrumb`, `add_crumb()` the same default "Home" label (`_x( 'Home', 'breadcrumb', 'woocommerce' )`) and home URL (`apply_filters( 'woocommerce_breadcrumb_home_url', home_url() )`) that function defaults to, then call `generate()` to get the crumb array. This keeps the JSON-LD `BreadcrumbList` output (built from this same array, further down in the file) consistent with whatever `woocommerce_breadcrumb()` actually renders visually on the same page.
- **Re-tested against the live site after the fix**: homepage and shop page both now return full, correct HTML (47KB/69KB, proper `<title>`, real theme markup, zero error/warning text) instead of 0 bytes.
- **Spot-checked every other `wc_get_*()` call in the theme** (`wc_get_page_id`, `wc_get_related_products`, `wc_get_product_visibility_term_ids`, `wc_get_product_term_ids`) against WooCommerce core to check whether this was an isolated mistake or a pattern — all four are real, confirmed-existing core functions. This appears to have been a one-off.
- **Lesson for this project, also saved to memory**: this function name was never actually verified against WooCommerce core source before being used, breaking from the practice (demonstrated everywhere else in this project — the related-products fallback, the sticky-cart `is_purchasable()` fix, the checkout `$data` array shape) of reading the actual installed plugin source rather than assuming a plausible-sounding function name exists. A single unverified assumption here caused a site-wide fatal that went undetected through an entire "quality gate" ticket because the audit was grep-based (checking patterns like escaping/nonces) rather than execution-based (actually loading a page) for most of its checks.
